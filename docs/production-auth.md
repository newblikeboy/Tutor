# Production account access

The operator requested working login and signup on the HTTPS droplet and explicitly chose password-only staff login. `AUTH_PROVIDER=password` enables non-sample parent/tutor accounts and provisioned mentor/admin/support/finance accounts, keeping `APP_ENV=production`. Missing/disabled authentication is still closed. MFA is not implemented or required under this user override.

Required configuration: `WEB_ORIGIN` must be an exact HTTPS origin without a trailing slash/path, credentials, query or fragment; `HTTP_ADDR` must bind a loopback IP such as `127.0.0.1:8080`. Nginx serves the frontend and proxies `/api/`, overwriting `X-Forwarded-For` with `$remote_addr`. Only a single parsed IP from a loopback peer is used for per-client limits; chains and direct untrusted peers are not trusted.

Existing Argon2id password protection, bounded password work, per-email/IP limits, unique normalized credentials, transaction-backed signup, HttpOnly/Secure/SameSite=Lax cookies, exact Origin, CSRF, expiry, rotation/revocation and ownership checks remain. Production sessions use a distinct persisted method (`password-production`) so development/legacy sessions cannot be replayed; they are likewise not accepted in development. Existing migrations accept this string; no new collection or schema migration is necessary for this release.

The operator-selected password policy is 8–128 characters for signup, password changes and staff provisioning. The existing common-password checks and Argon2id settings remain. Existing passwords/hashes are not changed; no reset or data migration is needed. Frontend hints, input constraints and generated OpenAPI definitions use the same minimum.

Every production login/session/private request checks that the user is not a sample and has one of the six recognized roles. Public signup accepts only parent/tutor; staff are created through the audited operator CLI, never by a public role selector. Staff sign-in uses the existing email/password form. The authenticated database role determines permissions, regardless of the selected login tab. Admin/mentor can use their assigned academic views; support/finance remain denied academic dashboards and application queues. Tutor signup creates an applicant and never grants academic approval or public discovery.

This is a bounded account-access release. Email ownership verification and password recovery/delivery are not implemented; registration does not claim email verification. Existing password change and session revocation work for signed-in users. The guardian-verification gate for real minor data and live payments remain closed. These outstanding workflows must be implemented/reviewed before their intended use; successful sign-in is not full platform readiness.

Deploy the new binary and frontend together before enabling the setting; older binaries reject it and produce a 502 behind Nginx. Keep the previous release. For rollback, first restore `AUTH_PROVIDER=disabled`, then select the older release and restart. Use a separate production database, never run sample seeding in production, and never switch the public API to development mode.

Verification includes real MongoDB replica-set production API tests over TLS for signup/login/logout, all four provisioned staff roles, role-specific denials, persistence across instances, password rotation, Secure cookie attributes, bad Origin/CSRF, sample/unknown-role rejection, development-session replay, expiry and proxy-aware limits. Config tests cover valid HTTPS/IP origins, explicit enablement, invalid origins and public API binding. Browser verification uses a locally built production API/frontend and an isolated loopback MongoDB database; self-signed TLS is accepted only by that local browser fixture. Actual droplet account verification follows operator deployment.
