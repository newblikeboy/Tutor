# Production parent and tutor accounts

The operator requested working login and signup on the HTTPS droplet. The previous release rejected `AUTH_PROVIDER=password` in production and always hid the forms. This release accepts that setting for non-sample parent/tutor accounts, keeping `APP_ENV=production`. Missing/disabled authentication is still closed.

Required configuration: `WEB_ORIGIN` must be an exact HTTPS origin without a trailing slash/path, credentials, query or fragment; `HTTP_ADDR` must bind a loopback IP such as `127.0.0.1:8080`. Nginx serves the frontend and proxies `/api/`, overwriting `X-Forwarded-For` with `$remote_addr`. Only a single parsed IP from a loopback peer is used for per-client limits; chains and direct untrusted peers are not trusted.

Existing Argon2id password protection, bounded password work, per-email/IP limits, unique normalized credentials, transaction-backed signup, HttpOnly/Secure/SameSite=Lax cookies, exact Origin, CSRF, expiry, rotation/revocation and ownership checks remain. Production sessions use a distinct persisted method (`password-production`) so development/legacy sessions cannot be replayed; they are likewise not accepted in development. Existing migrations accept this string; no new collection or schema migration is necessary for this release.

Every production login/session/private request checks that the user is not a sample and has the parent or tutor role. Public signup never provisions staff. Staff login remains blocked pending MFA, including direct API requests and a previously issued session whose user becomes staff. The staff screen explicitly explains that it is unavailable. Tutor signup creates an applicant and never grants academic approval or public discovery.

This is a bounded account-access release. Email ownership verification and password recovery/delivery are not implemented; registration does not claim email verification. Existing password change and session revocation work for signed-in users. Staff MFA and the guardian-verification gate for real minor data remain closed, as do live payments. These outstanding workflows must be implemented/reviewed before their intended use; successful signup is not full platform readiness.

Deploy the new binary and frontend together before enabling the setting; older binaries reject it and produce a 502 behind Nginx. Keep the previous release. For rollback, first restore `AUTH_PROVIDER=disabled`, then select the older release and restart. Use a separate production database, never run sample seeding in production, and never switch the public API to development mode.

Verification includes real MongoDB replica-set production API tests over TLS for signup/login/logout, persistence across instances, password rotation, Secure cookie attributes, bad Origin/CSRF, sample/staff rejection, development-session replay, expiry and proxy-aware limits. Config tests cover valid HTTPS/IP origins, explicit enablement, invalid origins and public API binding. Browser verification uses a locally built production API/frontend and an isolated loopback MongoDB database; self-signed TLS is accepted only by that local browser fixture. Actual droplet account verification follows operator deployment.
