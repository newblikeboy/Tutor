# Payment testing and Razorpay integration

The operator authorised temporary test checkout on 2026-10-10 because Razorpay keys are unavailable. Set `PAYMENT_PROVIDER=simulation` explicitly; no keys are needed. This is a Go/MongoDB implementation, with no external checkout script, charge or in-memory payment fallback. The default remains `disabled`; missing Razorpay credentials never silently select simulation. Production HTTPS, loopback binding, private sessions, role restrictions and sample-account denial remain in force.

Parent flow: choose classes -> Pay & confirm booking (test) -> GoCoaching test checkout -> Complete test payment -> Test payment successful -> confirmed classes. Closing checkout leaves the booking unpaid. Reopening resumes the saved order. The server creates a deterministic `sim_order_…`, derives the amount/currency from the saved agreement, and stores `provider=simulation`. The authenticated owner confirms via `POST /api/v1/billing/{id}/simulate` with `{ "confirmed": true }`. The capture transaction saves `sim_pay_…`, `state=captured` and `capturedAt`, promotes eligible class reservations, sets `paymentSimulated=true` on the enrollment, records one audit event and queues normal labelled booking notifications. Repeated confirmation returns the same capture without duplicated classes/notifications. Expired holds or changed tutor scope/availability fail explicitly without recording a successful capture.

Simulation records remain identifiable after configuration changes, including in parent/tutor booking views, payment history and booking/reminder emails. They are excluded from collection revenue and create no real finance booking, payment journal, tutor earning/payout, refund or paid invoice. Testing class recording and learner progress still works with normal assignment/time/version checks. Simulated bookings consume real teaching slots while active; cancel test bookings through normal controls when finished. Retain their history rather than converting them into real payments.

For the existing droplet, set this line in `/etc/tutor/api.env` after deploying the updated code:

```dotenv
PAYMENT_PROVIDER=simulation
```

Then restart `sudo systemctl restart tutor-api` and check `/api/v1/config` reports `payments: "simulation"`. Production does not auto-load the repository `.env`. Local development uses the ignored root `.env` instead. Set `PAYMENT_PROVIDER=disabled` to stop further test captures while keeping saved test records. Provider changes invalidate incompatible outstanding checkouts; let old holds expire and choose new dates.

The independent Razorpay adapter still requires private `RAZORPAY_KEY_ID` (`rzp_test_…`), `RAZORPAY_KEY_SECRET` and a separate `RAZORPAY_WEBHOOK_SECRET` with `PAYMENT_PROVIDER=razorpay` for labelled sandbox checkout. Development rejects live keys; the existing production Razorpay release gate remains closed pending provider acceptance/review. Obtaining live keys alone does not complete that acceptance. Switching payment configuration disables the simulation endpoint and never rewrites test captures into Razorpay payments.

Tuition fees are integer paise in immutable agreement versions. New Home weekly packages contain 6 classes and monthly packages 24 classes, scheduled across available teaching dates without a calendar-period deadline; staff package prices and saved agreements remain unchanged. New parent bookings directly place a 15-minute reservation while awaiting payment; tutor acceptance applies only to retained historical requests. Classes 1-5 use one All Subjects package fee; Classes 6-12 multiply the staff package price by selected subject count. Opening checkout stores an idempotent payment intent before creating a Razorpay order. An interrupted order request is reconciled by its receipt; it is never blindly recreated. Browser confirmation uses the stored order ID and a server-verified HMAC, followed by a provider payment lookup. A client callback alone cannot activate tuition. Verified capture activates eligible held classes without tutor acceptance.

`POST /api/v1/webhooks/razorpay` validates the exact raw body against the separate webhook secret before parsing, deduplicates event IDs/body fingerprints, and queues only references. Subscribe to `payment.captured`, `payment.failed`, `refund.processed` and `refund.failed`. The Go worker claims jobs with persisted leases and retries with backoff; failed jobs appear in finance/admin operations with explicit retry evidence. Payment capture, duplicate events and hold expiry serialize through MongoDB transactions. Late or unusable payments retain a financial record and create operator review; they do not reinstate expired teaching reservations.

Refund requests reserve the unrefunded amount atomically. A different finance/admin reviewer approves or rejects with evidence. Approved requests use `X-Refund-Idempotency` with the immutable request ID and amount. Submission is distinct from provider processing. Failed refunds release their reservation; processed refunds create one immutable journal. Capture journals debit gateway receivable and credit family prepaid; refund journals reverse that pair. These are not bank settlement records. The 75% guaranteed tutor payout, reviewed tax allocation, completed-class accounting, manual weekly payout verification and paid supplier invoice records are described in [finance.md](finance.md). Automated Route transfers, disputes/chargebacks, credit-note issuance and statutory tax remittance remain outside this implementation; no external payout is simulated.

Simulation acceptance: full real local MongoDB Go race/vet, frontend type/lint/sixteen tests/build and exact contract reproduction pass. Tests cover concurrent capture idempotency, ownership/role/amount denial, forged real-provider capture rejection, expiry, persisted activation and financial/email boundaries. Actual browser booking, closing/resuming checkout, capture/reload, tutor lesson recording, parent progress and payment history pass without any Razorpay request. Five new desktop/mobile captures and four refreshed existing views were inspected; exercised views pass axe/overflow checks. The ignored local `.env` explicitly selects simulation and restarted local API/Vite report readiness plus `payments=simulation`.

Earlier Razorpay adapter HTTP/signature and real-MongoDB transaction acceptance uses a test-only gateway boundary. Actual Razorpay sandbox checkout/webhooks, account configuration, refund settlement and browser provider interaction remain unexecuted without test keys and an operator-controlled HTTPS webhook endpoint. No live charge or refund has been sent by this change; production Razorpay acceptance remains separate.
