# Razorpay integration and outstanding launch checks

The user reports an approved Razorpay account. No credentials were printed or committed. Runtime uses a Go HTTPS adapter; no Node API, simulated checkout or fake success payment is available. Set `PAYMENT_PROVIDER=razorpay` with private `RAZORPAY_KEY_ID` (`rzp_test_…`), `RAZORPAY_KEY_SECRET` and a separate `RAZORPAY_WEBHOOK_SECRET` to enable labelled sandbox checkout. Development rejects live keys; production remains closed pending release review. The supplied private `.env` has not been changed.

Tuition fees are integer paise in immutable agreement versions. Tutor acceptance places a 15-minute reservation for a payable agreement. Opening checkout stores an idempotent payment intent before creating a Razorpay order. An interrupted order request is reconciled by its receipt; it is never blindly recreated. Browser confirmation uses the stored order ID and a server-verified HMAC, followed by a provider payment lookup. A client callback alone cannot activate tuition.

`POST /api/v1/webhooks/razorpay` validates the exact raw body against the separate webhook secret before parsing, deduplicates event IDs/body fingerprints, and queues only references. Subscribe to `payment.captured`, `payment.failed`, `refund.processed` and `refund.failed`. The Go worker claims jobs with persisted leases and retries with backoff; failed jobs appear in finance/admin operations with explicit retry evidence. Payment capture, duplicate events and hold expiry serialize through MongoDB transactions. Late or unusable payments retain a financial record and create operator review; they do not reinstate expired teaching reservations.

Refund requests reserve the unrefunded amount atomically. A different finance/admin reviewer approves or rejects with evidence. Approved requests use `X-Refund-Idempotency` with the immutable request ID and amount. Submission is distinct from provider processing. Failed refunds release their reservation; processed refunds create one immutable journal. Capture journals debit gateway receivable and credit family prepaid; refund journals reverse that pair. These are not bank settlement records. Commission allocation, tutor payable amounts, Route transfers, disputes/chargebacks and tax invoices still require implementation plus approved operating/tax policy; no invented commission or payout is recorded.

Verification so far: local adapter HTTP/signature tests and eight real-MongoDB transaction cases pass with race checks against a local replica set while Atlas capacity is blocked. Provider requests in those tests use a test-only gateway boundary. Actual Razorpay sandbox checkout/webhooks, account configuration, refund settlement and browser provider interaction remain unexecuted without test keys and an operator-controlled HTTPS webhook endpoint. No live charge, refund or external delivery has been sent.

Primary references checked during implementation: [create orders](https://razorpay.com/docs/api/orders/create/), [receipt reconciliation](https://razorpay.com/docs/api/orders/fetch-all/), [payment lookup](https://razorpay.com/docs/api/payments/fetch-with-id/), [normal refunds with idempotency](https://razorpay.com/docs/api/refunds/normal-refunds-idempotent), [webhook validation and ordering](https://razorpay.com/docswebhooks/validate-test/). Recheck provider documentation and staging CSP during live preparation. The droplet template currently has a restrictive same-origin CSP and must be reviewed against verified Razorpay resource requirements before enabling hosted checkout on that deployment.
